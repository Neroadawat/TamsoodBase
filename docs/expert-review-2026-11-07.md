# รีวิว TamsoodBase วันที่ 7 พฤศจิกายน 2569

TamsoodBase ใช้สำรวจสถิติพลังงานไทยและตรวจหลักฐานของกรณีศึกษาได้แล้ว งานสำคัญที่สุดก่อนขยายฐาน LCI คือทำให้ผลคำนวณทุกแถวชี้กลับไปยังค่าที่โปรแกรมอ่านจริง และแยกข้อมูลวัดจริง ค่าประมาณ และผลจำลองในฐานข้อมูลกับหน้าจออย่างสม่ำเสมอ

## สิ่งที่ตรวจรอบนี้

- ชุด Python unittest 245 รายการผ่านในเครื่อง ใช้เวลาประมาณ 20 วินาที ผลนี้ครอบคลุมชุดทดสอบที่ discover พบ
- เว็บจริง /healthz และ /readyz ตอบ 200 ในการตรวจครั้งเดียว /api/release ตอบข้อมูลรุ่นหน้าเว็บ /api/model ตอบ metadata กรณีศึกษาโดยมี full_lifecycle_inventory=false /api/reference.json รายงานทั้งหมด 97 รายการและปิดปริมาณ /api/reference.csv ตอบ 403 ตามนโยบาย /api/ethanol ตอบ 404 ณ เวลาตรวจ
- Chrome headless ที่ความกว้าง 390 และ 1440 พิกเซล เปิด catalog, NSO และ case study แล้วไม่พบแนวนอนล้นหรือ pageerror ในการตรวจนี้ หน้า case study บนเว็บแสดงไบโอดีเซลปาล์ม
- ตรวจโค้ดตัวสร้างกรณีเอทานอล, activity store, schema, Vercel proxy และทางส่งออกของ DMF เทียบกับรายงานส่งมอบวันที่ 6 พฤศจิกายน การตรวจรอบนี้ไม่มี browser UAT กับผู้ใช้จริง การทดสอบโหลด หรือการตรวจสิทธิทุกแหล่งซ้ำ

## 1. LCI และความน่าเชื่อถือทางวิทยาศาสตร์

**P0 สายหลักฐานคำนวณเอทานอลยังไม่ผูกกับค่าที่คำนวณจริง** scripts/build_ethanol_proxy_scenario.py อ่านรายงานสมดุลมวลและเช็ก hash ของ PDF แต่ src/ethanol_proxy_scenario.py ใช้ค่าคงที่ของปริมาณกากน้ำตาล ผลผลิต และฐาน 150,000 ลิตร/วัน ผมทดสอบในสำเนาชั่วคราวโดยแก้ค่ากากน้ำตาลใน JSON จาก 532.45 เป็น 999.99 ตัน/วัน ผลขนส่งยังเท่าเดิม จากนั้นเปลี่ยนช่วงไฟฟ้าใน JSON เป็น 1–2 kWh/วัน โปรแกรมสร้างผลใหม่ได้และยังอ้าง PDF hash เดิม กรณีแรกแสดงว่าแถวที่อ้างไม่ได้ขับผลคำนวณ กรณีที่สองแสดงว่า hash ของต้นฉบับอย่างเดียวไม่ตรวจความถูกต้องของค่าที่สกัด

เกณฑ์แก้คือให้ builder อ่านแถวสกัดที่มี ID, หน่วย, ตำแหน่งและฐานชัดเจน ตรวจ hash ของชุดแถวที่ผ่านการทวนสอบและบันทึก hash ของ input, สูตร และรุ่นโค้ดต่อ run การเปลี่ยนข้อมูลที่ได้รับอนุมัติต้องสร้างรุ่นใหม่และเปลี่ยนผลตามสูตร ส่วนการแก้ข้อมูลนอกขั้นอนุมัติต้องหยุดการสร้างผล ตรวจว่าสามารถสร้างผลซ้ำจากชุดหลักฐานเดียวกันบนเครื่องใหม่ได้

**P0 ฐานผลลัพธ์ต้องแยกตามคำถาม** เอทานอล 1 L ที่หน้าโรงงาน ใช้ตอบคำถามกระบวนการผลิต ขณะที่ผลรถทดลองเป็น g CO₂/km ตามเชื้อเพลิงและช่วงความเร็ว การเชื่อมต้องมีเชื้อเพลิงที่ใช้ต่อกิโลเมตร สูตรผสม และขอบเขตเบนซินที่รวมอยู่ การเปรียบเทียบเบนซินกับแก๊สโซฮอล์ต้องใช้บริการเดินทางเท่ากัน การแยก CO₂ ฟอสซิลและชีวภาพต้องอิงฐานคาร์บอนของส่วนผสม พร้อมจัดการ CH₄/N₂O แยกกัน

**P0 น้ำเสียต้องจับคู่จุดวัดและช่วงเวลา** TSM มีค่าจากเอกสารประเมินก่อนและหลังระเหยน้ำ และผลการเดินระบบที่รายงานต่างปี อัตรา 97% ของ MS-UASB คือค่าการเปลี่ยนเป็นมีเทนในชุดทดลอง ใช้เป็นเกณฑ์เทียบเทคโนโลยีเท่านั้น ควรทำตารางสัญญาข้อมูลรายงวดที่มีผลิตเอทานอล น้ำเข้า COD และจุดวัด ก๊าซกู้คืน ก๊าซปล่อย และไฟฟ้าเข้าออก การประเมิน CH₄ ต้องครอบคลุมการรั่ว มีเทนละลาย และก๊าซที่เผาไหม้ไม่หมดตามขอบเขตที่เลือก

**P1 ออกแบบสถานการณ์ให้ตอบคำถามคนละชุด** แยกกรณี DEDE, ข้อมูลเปรียบเทียบ มช., ระยะไปกลับจากการสัมภาษณ์ และ benchmark TSM ออกจากกัน ระยะ 150–500 กม. เป็นไปกลับ ส่วน 10/50/100 กม. ของตัวอย่างเดิมเป็นค่าที่กำหนดต่อเที่ยวขนส่ง ห้ามเทียบตัวเลขดิบก่อนแปลงฐานและกำหนดขากลับ ใช้ตัวชี้วัดคุณภาพข้อมูลแยกตามเวลา เทคโนโลยี พื้นที่ ความครบถ้วน และความน่าเชื่อถือ ช่วงต่ำ–สูงของแหล่งข้อมูลยังไม่มีการแจกแจงความน่าจะเป็น

**P1 ปิดงาน FAME แยกจากเอทานอล** กรณีปาล์มมีรุ่นและผลคำนวณภายในแล้ว แต่ทะเบียน elementary flow และ CF ที่อนุมัติยังเป็นศูนย์ตามหลักฐานสถาปัตยกรรม ควรปิดขอบเขตการจัดสรรภาระ การเชื่อมผู้ให้ข้อมูลพื้นหลัง และการทวนสมดุลอิสระก่อนอนุญาตคำนวณ LCIA การมี transaction และ FK รองรับความถูกต้องของการอ้างอิงในฐานข้อมูล ส่วนความถูกต้องด้านวิทยาศาสตร์ต้องทวนแยก

## 2. Web database และ database design

- **P1 ทำเส้นทางเผยแพร่แบบเดียวกัน** ปัจจุบันข้อมูลสำรวจ production, activity store ของ FAME และไฟล์หลักฐานเอทานอลอยู่คนละชั้น ควรเก็บ source document version → observation → normalized exchange → process dataset version → scenario/run → result → public projection โดยให้ผลและข้อมูลสาธารณะชี้ไปยังรุ่นที่ตายตัว เริ่มด้วยเอทานอลหนึ่งกรณีและทดสอบแถวจริงก่อนวาง migration กว้าง
- **P1 คุมสิทธิที่ระดับข้อมูล** แยก source URL, สิทธิแจกจ่ายตัวเลข, สิทธิแจกจ่ายไฟล์ และเหตุผลการตัดสิน การมี URL สาธารณะรองรับการชี้แหล่ง แต่สิทธิแจกจ่ายต้องตรวจแยก ปัจจุบัน reference ใช้ allowlist metadata และปิด CSV ซึ่งเป็นจุดแข็ง ให้ทดสอบการฉายข้อมูลชุดเดียวกันผ่าน list/detail/export และเส้นทางผิดพลาด
- **P1 แยกคุณภาพข้อมูลจากสถานะ workflow** การตรวจ hash การทวนค่ากับเอกสาร การวัดจริง การอนุมัติวิทยาศาสตร์ และการอนุญาตเผยแพร่เป็นคนละมิติ ใช้คอลัมน์ที่ตรวจได้และเหตุผลประกอบ เก็บ unknown พร้อมเหตุผล โดยไม่เปลี่ยนเป็น 0 และไม่ใช้สถานะ DONE ของงานแทนความพร้อมของข้อมูล
- **P1 รักษาโครงสร้างที่ดีที่มีแล้ว** ฐานกิจกรรมมี release seal, transaction และ FK ผูกผลกับ run/dataset รวมถึงตัวเลข Decimal ที่ตรวจแยกแล้ว ควรเพิ่มข้อกำหนดมิติหน่วย ทิศทาง flow ฐานผลผลิต และ observation provenance ให้ชัดก่อนขยายตาราง เสริมการทดสอบการแปลงหน่วยและการคงค่าต้นฉบับเมื่อย้าย SQLite ไป MySQL
- **P2 วัดดัชนีตามการใช้งานจริง** Explorer ใช้ LIMIT/OFFSET และ COUNT ตามเงื่อนไข กำหนดชุดคิวรีมาตรฐานสำหรับค้นตามปี ประเภท แหล่ง และสถานะ แล้วดู EXPLAIN กับข้อมูลขนาดจริงก่อนเปลี่ยนเป็น cursor หรือเพิ่มดัชนี ค่า export ที่โหลดแถวทั้งหมดเข้าหน่วยความจำใน explorer.py ควรวัดขนาดและ peak memory โดยเฉพาะเมื่อเพิ่มข้อมูล

## 3. UX/UI

- **P1 จัดเมนูตามเจตนา** แยก “ค้นสถิติ” “ตรวจแหล่งข้อมูล” และ “สำรวจกรณีศึกษา” ให้รู้จากการ์ดว่ากดเข้าไปเห็นปริมาณ เมทาดาทา หรือผลจำลอง ขณะนี้หน้า case study เป็น FAME ให้ตั้งชื่อให้ตรงและเพิ่มทางเข้าเอทานอลเมื่อ projection พร้อม
- **P1 ทำหน้ารายละเอียดหลักฐานให้เป็นรูปแบบเดียว** วางค่า หน่วย ฐาน ปี/ช่วงเวลา สถานะ และขอบเขตไว้ใกล้ตัวเลข แสดงคำว่า “รายงานจากโรงงาน” “สมมติฐาน” “ผลคำนวณ” และ “ยังขาดข้อมูล” ด้วยข้อความ ไม่พึ่งสีอย่างเดียว ให้มีปุ่มไปต้นฉบับพร้อมหน้าหรือตาราง
- **P1 เปรียบเทียบเฉพาะค่าที่เข้ากัน** หากหน่วยหรือฐานต่างกัน ให้โชว์สองบัตรพร้อมเหตุผลที่คำนวณผลต่างไม่ได้ สำหรับเอทานอลควรเปรียบเทียบพลังงานด้วยแถบช่วงและจุดอ้างอิง มช. ส่วนขนส่งใช้ตัวเลือกขาเดียว/ไปกลับพร้อมแสดงสมมติฐานการบรรทุก
- **P2 วัดภารกิจจากผู้ใช้จริง** ให้ผู้ใช้หาแหล่งอ้างอิงของหนึ่งตัวเลข แชร์ตัวกรอง และแยกค่าจริงจากกรณีจำลอง บันทึกเวลา ความสำเร็จ และคำที่ทำให้เข้าใจผิด ตรวจ keyboard, screen reader, zoom และ reduced motion หลังโหลดข้อมูลจริง ผล Chrome รอบนี้ยืนยันเพียงการเปิดสามหน้าที่สองขนาด

## 4. Frontend

- **P1 รักษาสัญญา URL และสถานะ loading/error/empty** NSO มีตัวกรองแชร์ได้จากงานก่อนหน้า กรณีศึกษาใหม่ควรเก็บ case และฐานใน URL ด้วย เพิ่มการทดสอบ deep link, reload, back, keyboard focus และ API ตอบช้าหลังเปลี่ยนหน้า
- **P1 แยกโมดูลตามหน้าที่ต่อจากงานเดิม** ใช้ API client กลางสำหรับ timeout/abort และ validation ของ schema ให้ render อ่าน view model แบบเดียวกัน ปัจจุบันมีการแยก story/discovery แล้ว จึงควรแยกส่วนเอทานอลออกเป็นหน่วยเล็กแทนการเพิ่มเงื่อนไขใน app.js ทั้งไฟล์
- **P2 วัด performance จริง** ทดสอบมือถือจำลองเน็ตช้า เก็บ LCP/INP/CLS และ payload ของหน้าหลัก หลังเปิดแต่ละเส้นทางให้วัดผลการแบ่งโหลดและ cache ไฟล์ตามรุ่น เวลาตอบ API ครั้งเดียวในรอบนี้ใช้เป็นเพียงสัญญาณวินิจฉัย

## 5. Full stack และงานปฏิบัติการ

- **P1 ลดความเสี่ยง Quick Tunnel** บันทึกสถานะ endpoint, รุ่น API และรุ่นข้อมูลคนละค่า หน้าเว็บและ release metadata เปิดได้แม้ backend ช้าหรือขาดการเชื่อมต่อ ควรมีปลายทางคงที่ภายใต้การควบคุมของทีม พร้อมแจ้งเตือน readiness และการทดสอบหลังเปลี่ยน origin
- **P1 ทำเพดาน export ที่ต้นทาง** Proxy มีเพดาน 32 MiB แต่เส้นทาง explorer สร้าง list และ CSV ทั้งชุดก่อนส่ง การจำกัดที่ proxy จึงควบคุมขนาดปลายทาง ส่วนต้นทุนฐานและหน่วยความจำต้องจำกัดใน backend ด้วย filter บังคับ, เพดานจำนวนแถว หรือ streaming จาก cursor ตามผลวัด
- **P1 ทดสอบขอบเขตสิทธิและความทนทาน** ใช้ test double กับ response ที่ช้า ถูกตัดกลางทาง ขนาดเกิน และประเภทข้อมูลผิด กำหนดนโยบาย deadline ทั้งคำขอและการยกเลิก upstream เมื่อ client ตัดการเชื่อมต่อ แยกเพดานตาม route การตรวจพบ 403 ของ CSV reference ยืนยันพฤติกรรมที่จุดนั้น
- **P2 ทำ release และ recovery ให้ทำซ้ำได้** ใช้ manifest ที่ผูก frontend, API, schema และ dataset releases ทำ smoke test ก่อน promote และระบุวิธีย้อนกลับ Backup/restore เดิมมีหลักฐานแล้ว ควรเพิ่มรอบตรวจตามเป้าหมาย RPO/RTO และวัดเวลา restore แบบแยกจากระบบจริง
- **P2 ลดความเสี่ยงส่งมอบจาก working tree ใหญ่** สถานะ git พบ 477 รายการในรอบนี้ รวมไฟล์งานและหลักฐานที่ยังอยู่ในเครื่อง ควรแยกชุดส่งมอบจาก manifest และทดสอบ clean checkout โดยรักษางานที่ยังแก้ของผู้ใช้และข้อมูลที่ติดสิทธิ

## ลำดับที่ควรลงมือ

| ลำดับ | งาน | เกณฑ์ผ่าน |
|---|---|---|
| 1 | ผูก builder เอทานอลกับ observation ที่ทวนแล้ว | ทดสอบเปลี่ยน mass และ energy แล้วตรวจพฤติกรรมได้ทั้งกรณีอนุมัติและแก้นอก workflow |
| 2 | จัดรุ่น case และแยกประเภทข้ออ้าง | DEDE, มช., TSM และชุดทดลองมี ID, basis, ช่วงเวลา, สิทธิ และสถานะแยก |
| 3 | สร้างหน้ากรณีเอทานอลจาก projection | ผู้ใช้เห็นที่มา สมมติฐาน ข้อมูลขาด และแชร์กรณีที่กำลังดูได้ |
| 4 | ปิดความเสี่ยง export และการเชื่อมต่อ | วัดขนาด หน่วยความจำ เวลา และตรวจปลายทางเมื่อ API ขัดข้อง |
| 5 | เพิ่มข้อมูลที่มีผลต่อ LCI รวม | มีหลักฐานหม้อไอน้ำ ขนส่ง การใช้ และ CH₄ ที่เข้ากับฐานเดียวกัน หรือระบุสมมติฐานเฉพาะรายกรณี |

การรีวิวนี้บันทึกผลตรวจและข้อเสนอ ส่วนการแก้โค้ดควรเริ่มที่ข้อ 1 เพื่อให้กรณีเอทานอลที่ขึ้นหน้าเว็บสามารถตรวจย้อนหลังได้ตั้งแต่วันแรก
